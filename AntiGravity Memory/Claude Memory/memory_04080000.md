### 4. L2.5 快取代理層（Form1_ComL3.vb）
呼叫順序：① 記憶體命中 → ② DB lazy SELECT → ③ L3 COM
```vb
GetCachedMailCount(folder)            ' 單一資料夾郵件數，有 DB lazy + snapshot 驗證
GetCachedFolderCount(folder)          ' 單一資料夾子資料夾數，有 DB lazy + snapshot 驗證
GetCachedMailCountAllAsync(folder)    ' 整棵子樹郵件總數，有 DB lazy
GetCachedFolderCountAllAsync(folder)  ' 整棵子樹資料夾總數，有 DB lazy
GetCachedFolderSizeAsync(folder)      ' 單一資料夾大小，有 DB lazy
GetCachedFolderSizeAllAsync(folder)   ' 整棵子樹大小，有 DB lazy
GetCachedMailWithAttachment(folder)   ' Tab3 Phase1，有 DB lazy (mail_basic)
GetCachedAttachFilename(mail)         ' Tab3 Phase2，有 DB lazy (mail_attachments)
```
輔助函數：
- `GetLivePrContentCount(folder)`：單次 PropertyAccessor 讀 PR_CONTENT_COUNT，用於 snapshot 驗證（< 1ms）
- `PopulateFolderCacheFromDbRow(fPath, row)`：DB 命中時一次填滿六個記憶體快取（只填 NOT NULL 欄位）
- `HasCachedSubFoldersFast(folder)`：快速預測子資料夾有無，TreeView 展開用（目前 comment out 中）

### 5. Snapshot 驗證原則
- DB 存的 `content_count_snapshot` = save 時的 `PR_CONTENT_COUNT` 值
- L2.5 讀 DB 後呼叫 `GetLivePrContentCount` 比對，相同才用 DB 值
- **例外**：`BuildBfsFolderTree` 的剪枝決策不驗 snapshot（容忍略舊，避免多一次 COM call）

## SQLite 持久化快取（Form1_SQLite2.vb）

### 四張表結構
```sql
folder_stats   (folder_path PK, mail_count, mail_count_all, folder_count, folder_count_all,
                folder_size, folder_size_all, content_count_snapshot, updated_at)
mail_basic     (entry_id PK, folder_path, subject, msg_size, received_time, sender_name,
                attach_count, item_count_snap, updated_at)
mail_attachments (entry_id PK, folder_path, filenames TEXT JSON, msg_size, updated_at)
year_counts    (folder_path+year PK, count, updated_at)   ← 2026-04-08 新增
```
- DB 路徑：`Application.StartupPath\OLAcache.db`
- 不需要 store_id 欄位：FolderPath 天然包含 PST store 名稱，EntryID 跨 PST 不碰撞

### 重大 Bug 修正記錄（2026-04-07）
**SaveFolderStatsInner**：`TryGetValue` miss 時 Integer 預設值為 0，`0` 與「真的是 0 個子資料夾」無法區分。
修正：用 `hasXxx = TryGetValue(path, xxx)` 判斷有無測量過，未測量的欄位寫 `DBNull.Value`（SQL NULL）。

**LoadFolderStatsInner**：原本直接 `reader.GetInt32(N)` 沒有 `IsDBNull` 保護。
修正：每欄加 `If Not reader.IsDBNull(N) Then` 保護，NULL 欄位不塞入記憶體快取。

**根因說明**：若把 -1 或 0 寫入 DB，LoadFolderStatsInner 讀回後塞進記憶體快取，GetCachedFolderCount 記憶體命中回傳 0 → LoadSubFolderToTreeView 判斷 `> 0` 為 False → TreeView 不顯示 "+" 加號。

### Friend 函數清單

## 已確認的死路（PST 限制，勿再嘗試）

- DASL/Restrict 無法篩附件檔名（PST 無索引）
- `AdvancedSearch` 在 LTSC 失敗（HResult=0x8007064F）
- `SetColumns` 加 `PR_ATTACH_LONG_FILENAME` → NullReference（附件是子物件屬性）
- `PR_MESSAGE_SIZE_EXTENDED (0x0E080014)` 和 `PR_MESSAGE_SIZE (0x0E080003)` 在 PST folder object 均回「未知」
- `GetTable + GetArray()` 無法取附件檔名（附件在 message row 的下層）
- PST 同檔 Parallel 效能無提升（單檔 I/O lock 競爭）；跨 PST Task.WhenAll 才真正有效

## 全域架構原則（不變）

### COM / 執行緒規則
- 所有 Outlook COM 呼叫必須在 UI 執行緒（STA），不可用 Task.Run 包住
- `Await Task.Delay(1)` 讓 UI 不凍結（高頻迴圈勿用 Task.Yield()，代價 5~15ms）
- Redemption 是 free-threaded，可在 Task.Run / Parallel.ForEach 中呼叫
- `_cancelRequested` 全域旗標統一控制 ESC 中斷
- SQLite I/O 在 Task.Run 背景執行緒，不在 UI 執行緒

### Outlook Namespace 衝突
- `System.Exception`、`System.Windows.Forms.View.Details` 必須寫全名
- 不可縮寫 namespace（Imports Outlook 會衝突）

### L3 函數設計原則
- Fallback 鏈：⓪ Redemption → ① MAPI PropertyAccessor → ② OOM → ③ return -1
- 失敗統一回傳 -1（不回 0）
- Finally 中統一釋放 COM 物件（`TryMarshalRelease()`）

### Redemption 整合狀態
- `InitRdoSession()` 存在但在 `Form1_Load` 中被 comment out
- `PreloadAttachmentCacheRDOAsync` 保留，`_rdo IsNot Nothing` 時自動啟用 RDO 平行預載
- 效能測試：OOM ~50封/s，RDO ~120封/s（同一PST，只有 2.5x，因 PST I/O lock 是瓶頸）
