### 4. L2.5 快取代理層（Form1_Outlook.vb）
呼叫順序：① 記憶體命中 → ② DB lazy SELECT → ③ L3 COM
```vb
GetCachedMailCount(folder)            ' 單一資料夾郵件數，有 DB lazy + snapshot 驗證
GetCachedFolderCount(folder)          ' 單一資料夾子資料夾數，有 DB lazy + snapshot 驗證
GetCachedMailCountAllAsync(folder)    ' 整棵子樹郵件總數，有 DB lazy
GetCachedFolderCountAllAsync(folder)  ' 整棵子樹資料夾總數，有 DB lazy
GetCachedFolderSizeAsync(folder)      ' 單一資料夾大小，有 DB lazy
GetCachedFolderSizeAllAsync(folder)   ' 整棵子樹大小，有 DB lazy
GetCachedMailWithAttachs(folder)      ' Tab3 Phase1，有 DB lazy (mail_withattachs)
GetCachedAttachFilename(mail)         ' Tab3 Phase2，有 DB lazy (attach_filenames)
```
輔助函數：
- `GetLiveFolderSnap(folder)`：單次 PropertyAccessor 讀 PR_CONTENT_COUNT，專門用於 snapshot 驗證（< 1ms）；失敗回 -999（永遠不等於合法 snap 值）
- `FillFolderCacheFromDbRow(fPath, row)`：DB 命中時一次填滿六個記憶體快取（只填 NOT NULL 欄位）
- `HasSubFoldersFast(folder)`：快速預測子資料夾有無，TreeView 展開用（記憶體→DB→COM 三層）

### 5. Snapshot 驗證原則
- DB 存的 `content_count_snapshot` = save 時的 `GetLiveFolderSnap()` 值
- L2.5 讀 DB 後呼叫 `GetLiveFolderSnap` 比對，相同才用 DB 值
- **例外**：`BuildBfsFolderTree` 的剪枝決策不驗 snapshot（容忍略舊，避免多一次 COM call）
- **為何不直接用 `GetMailCount` 做驗證**：`GetMailCount` 是 L3 有三層 fallback 的完整呼叫；`GetLiveFolderSnap` 是無副作用的輕量函數，失敗語意不同（-999 vs -1），且不可用 L2.5 `GetCachedMailCount` 驗快取（雞生蛋問題）

### 6. HasSubFoldersFast 設計
- 呼叫順序：① `_cacheFolderCount` 記憶體 → ② `DbGetFolderStats(fPath).fc` → ③ `folder.Folders.Count` COM
- 已在 `LoadSubFolderToTreeView` 第 489 行啟用，解決 DB 載入後 TreeView 不顯示 "+" 的問題
- 比直接 `folder.Folders.Count` 快：記憶體命中~0μs，DB命中~0.1ms，COM才~1-5ms

## SQLite 持久化快取（Form1_SQLite2.vb）

### 五張表結構（2026-04-09 新增 month_counts）
```sql
folder_stats   (folder_path PK, mail_count, mail_count_all, folder_count, folder_count_all,
                folder_size, folder_size_all, content_count_snapshot, updated_at)
mail_withattachs (entry_id PK, folder_path, subject, msg_size, received_time, sender_name,
                  attach_count, item_count_snap, updated_at)
attach_filenames (entry_id PK, folder_path, filenames TEXT JSON, updated_at)
                -- 注意: msg_size 欄位仍在 schema 中但 INSERT 時不傳（永遠 NULL）
                -- SaveAttachFilenamesInner 不列 msg_size 在 INSERT 欄位清單，讓 SQLite 自動填 NULL
                -- 原因: SqliteType.Integer + DBNull.Value 在 Microsoft.Data.Sqlite 拋 "Value must be set"
year_counts    (folder_path+year PK, count, updated_at)
month_counts   (cache_key+month PK, folder_path, count, updated_at)
                -- cache_key = FolderPath & "_" & year，folder_path 另存供 CleanupOrphan 清除
```
- DB 路徑：`Application.StartupPath\OLAcache.db`
- `GetDatabaseSummary()` 回傳 tuple：`(fc, mb, at, yc, mc, kb)` — 2026-04-09 加入 `mc`

### Friend 函數清單
```vb

RenewMailWithAttachsAsync(folder, fPath) ' 三路比對更新 mail_withattachs（2026-04-09 新增）
GetDatabaseSummary() → (fc,mb,at,yc,mc,kb)
DbGetFolderStats(folderPath)
DbGetMailwithAttachs(folderPath)
```

### RenewCacheAsync 六階段流程（2026-04-09）
```
Phase 1. BFS 掃出所有 live folders（COM）
Phase 2. 每個 folder: GetLiveFolderSnap vs DB snapshot → 找 dirty folders
Phase 3. 對每個 dirty folder 重新計算：
           mc/fc（~1ms）
           year_counts（GetTable + GetArray）
           month_counts（清記憶體，Phase5 清 DB，展開時 lazy 重算）
           mail_withattachs（RenewMailWithAttachsAsync 三路比對）
           folder_size（選擇性，依 includeSize，CheckBox: RenewIncludeSize）
           清除 mca/fca/fsa 聚合快取
Phase 4. 清除 dirty folders 的 ancestor 聚合快取
Phase 5. 批次 DELETE dirty folders 的 month_counts DB rows
Phase 6. CleanupOrphanFolderPath → SaveCachesToSQLiteAsync
```

### RenewMailWithAttachsAsync 三路比對
- 新郵件（live 有、DB 沒有）→ 進新 mailList，SaveCache 時 INSERT
- 已刪郵件（DB 有、live 沒有）→ 從 `_cacheAttachFilename` 清除（DB row 留 CleanupOrphan）
- 未變郵件（交集）→ filenames 快取保留，不重掃附件
- attach_filenames 永不重掃（設計邊界）

### Setting Tab 按鈕對應
- `SaveCache.Click`：`SaveCachesToSQLiteAsync()`
- `LoadCache.Click`：`LoadCachesFromSQLiteAsync()` + `GetDatabaseSummary()` 顯示
- `RenewCache.Click`：`RenewCacheAsync(RenewIncludeSize.Checked)`（2026-04-09 重構）
- `RenewIncludeSize`（CheckBox）：控制 RenewCache 是否重算 folder_size
- `ClearCache.Click`：清除記憶體快取字典

### Bug 修正記錄
**SaveAttachFilenamesInner（2026-04-09 修正）**：
- 錯誤：`cmd.Parameters("@sz").Value = DBNull.Value` 對 `SqliteType.Integer` 參數丟 `"Value must be set"`
- 根因：Microsoft.Data.Sqlite 的 `SqliteParameter.Bind()` 拒絕 `SqliteType.Integer + DBNull.Value` 組合
- 修正：`INSERT` 欄位清單移除 `msg_size`，讓 SQLite 自動填 NULL；同時移除 `@sz` parameter
- 此錯誤與郵件內容無關，第一筆就會炸，不是某封郵件觸發

## 已確認的死路（PST 限制，勿再嘗試）

- DASL/Restrict 無法篩附件檔名（PST 無索引）
- `AdvancedSearch` 在 LTSC 失敗（HResult=0x8007064F）
- `SetColumns` 加 `PR_ATTACH_LONG_FILENAME` → NullReference（附件是子物件屬性）
- `PR_MESSAGE_SIZE_EXTENDED (0x0E080014)` 和 `PR_MESSAGE_SIZE (0x0E080003)` 在 PST folder object 均回「未知」
- `GetTable + GetArray()` 無法取附件檔名
- PST 同檔 Parallel 效能無提升（單檔 I/O lock 競爭）；跨 PST Task.WhenAll 才有效
- `Microsoft.Data.Sqlite`：`SqliteType.Integer` 參數不可設 `DBNull.Value`（丟 "Value must be set"）；INSERT 時不列該欄位讓 SQLite 自動填 NULL 是正確做法

## 全域架構原則（不變）

### COM / 執行緒規則
- 所有 Outlook COM 呼叫必須在 UI 執行緒（STA），不可用 Task.Run 包住
- `Await Task.Delay(1)` 讓 UI 不凍結（高頻迴圈勿用 Task.Yield()，代價 5~15ms）
- Redemption 是 free-threaded，可在 Task.Run / Parallel.ForEach 中呼叫
- `_cancelRequested` 全域旗標統一控制 ESC 中斷
- SQLite I/O 在 Task.Run 背景執行緒，不在 UI 執行緒

### Outlook Namespace 衝突
- `System.Exception`、`System.Windows.Forms.View.Details` 必須寫全名
- 不可縮寫 namespace（Imports Outlook 會衝突）

### L3 函數設計原則
- Fallback 鏈：⓪ Redemption → ① MAPI PropertyAccessor → ② OOM → ③ return -1
- 失敗統一回傳 -1（不回 0）
- Finally 中統一釋放 COM 物件（`TryMarshalRelease()`）

### Redemption 整合狀態
- `InitRdoSession()` 存在但在 `Form1_Load` 中被 comment out
- `PreloadAttachmentCacheRDOAsync` 保留，`_rdo IsNot Nothing` 時自動啟用 RDO 平行預載
