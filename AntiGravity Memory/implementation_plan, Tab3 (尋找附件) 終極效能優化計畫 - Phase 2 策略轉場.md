# Tab3 (尋找附件) 終極效能優化計畫 - Phase 2 策略轉場

測試結果非常明確：「測試成功回傳 0 筆」代表 Outlook 的 PST/GetTable 查詢引擎，在本地端**拒絕展開 Sub-object (附件) 的內容進行 LIKE 比對**。

這個殘酷的事實證實了您當初的作法與 Claude 最終的妥協是**正確且唯一**的路：**只要涉及到檔名比對或個數比對，就絕對無法逃避 `GetItemFromID` (Phase 2 實例化) 這個成本。**

既然這是一道「必須繳的過路費」，我們的優化策略必須全面轉向：**「如何少繳費」以及「如何只繳一次」。**

---

## 修正後的優化核心策略

### 💡 戰略 1：漏斗嚴格化 (盡可能減少 Phase 2 的處理量)
既然進入 Phase 2 開信很貴（一次幾毫秒，3000 封就卡好幾秒），我們就要確保送進去開信的數量降到最低。
目前程式碼已經做得不錯，在進入 Phase 2 之前先做了 LINQ 大小過濾。我們將確保這個邏輯的絕對穩定：
*   先過濾大小，把不符合大小的信直接踢掉，**剩下的才送進 Phase 2 去開信查檔名**。

### 💡 戰略 2：深度快取分離 (Phase 1 基礎快取 與 Phase 2 條件快取)
這就是您提到的「分成二個快取去讀不同的目的」。既然查檔名這麼慢，我們就把它「快取」起來！
我們將設計兩套快取：
1. **基底快取 (`_tab3Phase1Cache`)**：
   * 存什麼：該資料夾所有「有附件的信」的清單 (只含 Subject, Size, EntryID，不含檔名)。
   * 何時用：只要搜尋這個資料夾，必定先讀它。
2. **條件快取 (`_tab3Phase2Cache`)**：
   * 存什麼：已經艱辛執行完 Phase 2 (打開過 MailItem 算完個數、比對過檔名) 後產生的 `List(Of ListViewItem)` 結果。
   * Cache Key：`{FolderPath} | {Keyword} | {MinSize}_{MaxSize}` (例如：`\\Gmail\Inbox | pdf | 200KB_10MB`)
   * 何時用：當使用者搜尋完全相同的條件時，**直接繞過 Phase 1 與 Phase 2，在 0.01 秒內把結果印到畫面上。**

### 💡 戰略 3：UI 不卡死的節流微調 (Throttling)
既然要開信，UI 卡頓是免不了的。目前您在 Phase 2 用了 `Await Task.Delay(1)` 搭配 `Stopwatch` 來節流，這是對的。
但在極端狀況下（如圖 3 雖然只找到 3 封，可是母體可能有幾千封需要比對），我們可以微調這個延遲邏輯（例如每處理 50 封才讓出一次 UI 線程），這可以在「處理速度」與「UI 反應」間取得更好的甜蜜點。

## 具體執行步驟 (Proposed Changes)

#### 1. 新增第二層快取容器
宣告一個全新的 Dictionary 來儲存條件搜尋結果。當資料夾信件總數改變（也就是有新信進來或刪除信）時，連同第一層快取一併作廢。

#### 2. 修改主控流程 (`Button3_Click`)
邏輯重構為：
1. 計算快取 Key：判斷目前的過濾條件 (大小、名稱、個數)。
2. 有無現成條件快取？
   * 有 ➡️ 直接從 `_tab3Phase2Cache` 取出 ListView 陣列顯示。**（極速完成）**
   * 無 ➡️ 繼續往下。
3. 讀取 Phase 1 基底快取 (同原來流程)。
4. 如果有勾「大小」：在記憶體作 LINQ 篩選。
5. 如果有勾「檔名」或「個數」：
   * 送入 `ScanAttachmentByName` (Phase 2)。
   * **(重要新增)** 將 Phase 2 傳回的 ListViewItem 陣列存入 `_tab3Phase2Cache` 中。

#### 3. 移除無效代碼
* 將我們剛剛掛上去的 DASL 測試程式碼與無關的註解移除，確認代碼整潔。

## 結論與下一步
不能將檔名搜尋下放給 Exchange Server 雖然可惜，但也完全解開了我們的疑惑：現在這條路，就是唯一且最佳的路。

加上「條件快取」機制後，使用者第一次搜尋某個 PDF 可能要等 1-2 秒，但如果他發現找錯了，想改個排序或是重搜一次，速度就會變成瞬間。而且他不管怎麼切換，都不會破壞原本的基礎快取。
