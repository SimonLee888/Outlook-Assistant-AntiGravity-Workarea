## 一、任務背景（事實）

- Tab3 附件檔名搜尋，啟用 RDO preload 平行讀取附件檔名（讀入 `_cacheAttachFilename`，key = `mail.EntryID`）。
- 既有兩個可正常運作的版本：
  - `RdoPreloadAttach_1`：`Parallel.ForEach`，共用 `_rdo`。
  - `RdoPreloadAttach_2`：`Task.WhenAll` + `SemaphoreSlim`，共用 `_rdo`。
  - 兩者皆使用 `_rdo`（其 `MAPIOBJECT = _olNS.MAPIOBJECT`，即共用 Outlook OOM 的 MAPI session）。
- 本輪目標：嘗試做 `RdoPreloadAttach_3`，改用「每執行緒/每 PST 各自獨立的 `RDOSession`」，試圖跨多個 PST 真正平行，繞過共用 session 的序列化。新增 radio button `RDO_Parallel3` 切換。

## 二、環境關鍵數據（事實）

- PST 總數約 27 個（OOM `_olNS.Stores` 列出 27 個 store）。
- `MailItemInfo` 結構欄位：`EntryID, Subject, Size, RcvTime, SenderName, AttachCount, FolderPath, MsgIDhash, SenderEmail`。**無 StoreID 欄位。**
- `FolderPath` 格式為 `\\StoreDisplayName\sub\...`（store 顯示名可含逗號、空格、底線、`&`、`~`、`@`，但不含反斜線）。
- Redemption 版本：6.7.0.6412。
- `_olApp = New Outlook.Application`、`_olNS = _olApp.GetNamespace("MAPI")`；啟動前強制 `Process.GetProcessesByName("OUTLOOK")` 必須存在 → 實為 attach 到正在執行的 Outlook（single-instance COM），使用其預設 profile。
- `_olApp` / `_olNS` 在 `Form1_Outlook.vb` 最前面宣告，於 `InitOutlookNamespace()` 初始化。

## 三、各次實測的【實測事實】

### 3-1. 早期 spike（SpikeRdoIndependentSession，測試資料夾 `\\Gmail_2022\收件匣\RdoTest\`，10~12 封含附件信）
- 步驟1：獨立 `RDOSession` + `Logon("","",False,True)` 成功，未被 PST 鎖擋住。
- 步驟2：獨立 session 以「導覽方式」（`Stores` 找名稱 → `IPMRootFolder.Folders.Item(...)` → `Items`）讀到全部信件附件檔名（含一封 55 個附件的信）。
- 步驟3a/3b：該獨立 session 讀出的 `EntryID`，以 OOM `_olNS.GetItemFromID(entryID)`（單參數）與 `GetItemFromID(entryID, storeID)`（帶 OOM StoreID）**都能還原**成 live MailItem。
- **注意**：此 spike 用的 Gmail_2022 後來發現屬於「profile 自動載入的 5 個 store」之一，可能因此造成「獨立 session 能涵蓋所有 PST」的錯誤信心。

### 3-2. RdoPreloadAttach_3 第一版（單參數 GetMessageFromID，扁平 thread-local 池）
- 輸出視窗被 `System.Runtime.InteropServices.COMException`（first-chance，'Outlook Assistant.dll'）洗版。
- progressbar2 完全不動、ESC 無反應、無法得知進度。

### 3-3. RdoPreloadAttach_3 第二版（補 StoreID + 預檢防洪）

### 3-4. RdoPreloadAttach_3 第三版（一 PST 一 session、組內循序、組間平行，用 `sess.Stores.Item(i).Name = storeName` 比對）
- 涵蓋 20 個 PST → 開 20 條 session。
- 大量 debug：「獨立 session 找不到 store [工作郵件存檔, 2015~2016, Toshiba]，跳過該組 1151 筆」等，幾乎每組都找不到 store。
- 最終：處理 43 筆、resolve 失敗 3669 筆。
- 早先未分組版（手動測 1~2 PST）實測速率：1 PST ≈ 30–40 封/秒；2 PST ≈ 50–60 封/秒。`_1`/`_2` 在相近情境曾達 100+ 封/秒。

### 3-5. SpikeDumpStoreIdentity（傾印 OOM 與獨立 RDO session 的 store 識別屬性）

## 四、Claude 的【待驗證推論】（全部存疑，待重新檢驗）

> 以下是 Claude 對上述事實的解釋。Simon 認為多處值得商榷。**重新驗證時請逐條當作「假設」對待，用 3 節的事實去證實或推翻，不要預設為真。**

- 【待驗證】`_1`/`_2` 能用單參數 `GetMessageFromID(entryID)` 成功、`_3` 獨立 session 失敗，是因為「共用 session 繼承 Outlook 的 store 上下文，獨立 session 沒有」。
- 【待驗證】3-2 的 COMException 洗版 + UI 卡死，是「每封信 GetMessageFromID 在獨立 session 解不開 → first-chance 例外洪流餓死 UI 執行緒」。
- 【待驗證】3-4 大量「找不到 store」，是因為「FolderPath 根名是 Outlook **顯示名**，RDO `Stores.Item(i).Name` 是 PST **內部原始名**，改過顯示名的 PST 對不上」。← 此推論尚未用實測直接證實（沒有 dump 過 RDO Name vs OOM DisplayName 的逐一對照）。
- 【待驗證・關鍵爭點】3-5 顯示「獨立 session 只看到 5 個 store，缺 22 個 `\Work\` PST」，Claude 推論為「那 22 個是手動『開啟資料檔』掛載、只存在於當前 Outlook 行程記憶體、未寫入 profile，故新獨立 session 看不到」。
- 【待驗證・矛盾未解】3-7 顯示「掛載前按路徑就找得到目標、store 數前後皆 6 未變、信數 31103」。Claude 推論為「先前某次 `AddPSTStore` 已把該檔持久寫入 profile，故這次 logon 前就可見；31103 是多 store 信數總和，代表檔確實開著可讀、不撞鎖」。
  - **但這與 3-5「獨立 session 只看到 5 個」直接衝突，Claude 用「profile 被先前 spike 改動」來圓，此圓說本身未經獨立驗證。**
  - **store 數始終 = 6（非 5、非 7）這件事，Claude 沒有完全解釋清楚。** 3-5 說 5 個、3-6/3-7 說 6 個，差異來源不明。
- 【待驗證】`AddPSTStore` 是「持久寫入 MAPI profile」的操作（而非臨時掛載）。← 影響「是否已污染 Simon 的 profile」這個善後判斷，需確認。
- 【待驗證】獨立冷 session 每封信成本約為 Outlook 熱 session 的 3 倍（依 35 vs 100+ 封/秒推估，非直接量測單封成本）。

## 九、本輪通用教訓（適用於下個對話）

- **印值要印完整**：`Left(x, 40)` 截斷 PstPath / StoreID 兩度造成判讀錯誤（誤以為值都一樣）。比對識別碼時不可截斷。
- **識別 store 一律用檔路徑（PstPath / FilePath），不要用 Name**：Name 在 OOM（顯示名）與 RDO（內部名）兩邊語意不同，且會誤命中。
- **不要憑推論直接寫 API**：本輪 `.StoreID`（RDOStore 無此屬性）即為憑空猜測致 late-bind 失敗的例子。不確定的 RDO 屬性/方法名，用 `CallByName` 多候選探測再用。
- **spike 的判讀條件要嚴**：v1 用「第一層資料夾抓樣本」+「名稱比對」雙重鬆散條件，導致空結果被當成功。驗證掛載是否真的成功，應以「實際信件數量」這種強證據。
