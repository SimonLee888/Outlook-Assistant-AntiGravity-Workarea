## 0. 一句話結論
Tab1「重啟後第一次全選」慢 5-7 秒,**根本原因 = `GetSortedSubFolders` 的 ② 分支對整棵樹每個子夾呼叫 `_olNS.GetFolderFromID` 逐夾物化 COM Folder**(暖重啟無法剪枝,被迫走訪全樹)。Option A = 暖路徑改走純 DB id-tree、零 COM 物化、聚合在記憶體重算。探針實測:DB-only 走樹 **120ms** vs GetFolderFromID 物化 **2185ms/767 次**。

---

## 1. 背景:這如何浮現
- 6/27→6/28 做了 **Stage2 重構**:`GetSubtree` 回傳合約由 `(folder, fPath)` 改為純資料 tuple `(eid, sid, fPath)`,消除 build 期 ~950ms 的 OOM folder 物化。
- 副作用:Tab2-5 的「B群 thunk」消費者在熱路徑**眼物化** `GetFolderById`,造成 regression。**已修復(Option X/Y,見 §6)**。
- Tab1 走的是**自己獨立的 BFS 路徑**(非 Tab2-5 的 proxy),其暖重啟慢是**另一個獨立問題**,即本檔主題。

## 2. 根本原因(經探針釘死,非推論)

### 暖重啟 Tab1 全選的資料流
`ComputeTab1FolderStats` → `CollectFolderStatsByBFS(rootFolder)`(Form1_MainTab12.vb ~338),拆成 5 步:
- **Step1 `BuildBfsFolderTree`**(~426):BFS 展開整棵樹。每節點:
  - ① 查 `_cacheMailCountAll` + `_cacheFolderCountAll`(暖重啟記憶體空 → **必 miss → isHit=False**)
  - ② `DbGetFolderStats(fPath)` → `FillCacheFromDbRow(…, skipAggregates:=True)`(填 mc/fc/fs 進記憶體,**不填** mca/fca/fsa)
  - 因 isHit 永遠 False → **不剪枝 → 展開所有子夾**,靠 `GetSortedSubFolders(curr.folderObj, fPath)`(line ~478)
- **Step2 `FetchDirectMailCountsAsync`**(~498):對 `Not IsFromCache` 節點呼叫 `GetMailCount(entry.Folder, fPath)` → ① `_cacheMailCount` 命中(Step1 已填)→ 快,**snap 在此被繞過**
- **Step3 `SummarizeSubTreeBottomUp`**(~532):純記憶體 bottom-up 加總(利用 BFS 父 index < 子 index)
- **Step4 `UpdateFolderStatsCache`**(~551):把重算的 mca/fca 寫回記憶體快取
- **Step5 `GetBfsResult`**:挑出 root + 直屬子夾給 UI

### 真兇:GetSortedSubFolders ②(Module_Outlook.vb ~556)
- ① `_cacheFolderTree`(key=`fPath|True/False` 依 `_showAllFolders`)→ 暖重啟空,miss
- ② `DbGetOrderedSubFolderIDs(fPath, _showAllFolders)` 拿子夾 id(快),**接著對每個 id 呼叫 `_olNS.GetFolderFromID(row.eid, row.sid)` 物化成 live COM Folder(line ~586)** ← **就是這裡**
- ③ `pFolder.Folders` COM 列舉(只有 ② 也 miss 時才走)

暖重啟 = 走訪全樹(~767 夾)× 每夾一次 `GetFolderFromID` ≈ 2.2s(孤立量測);真實 5-7s 還疊了 `IsMailFolder`、排序、`_cacheFolderTree` 寫入、BFS 節流、Step2 再跑一趟。但**物化是唯一能整塊拿掉的大頭**。

### 為何不能直接信 DB 的聚合來剪枝(關鍵約束)
`FillCacheFromDbRow` 的 `skipAggregates:=True`(2026/04/25「選項A」修正,Module_Outlook.vb ~2717):
- DB 的 `mca/fca/fsa` 帶 `_showAllFolders` **模式語意**,DB 沒記錄是哪個模式存的。
- 若直接信 DB 聚合剪枝 → 切模式或重啟後第一次統計會顯示**舊模式的錯誤加總**(bug)。
- 故 BFS 刻意不信 DB 聚合、自行展開重算 → 這就是被迫全展開的源頭。
- **Option A 的解法:聚合在記憶體重算(非信 DB)→ 模式天然正確,且不需要物化 folder 就能走樹。**

## 4. Option A 設計(下階段實作目標)

**目標**:Tab1 暖重啟(DB 存在)時,**完全不物化 COM Folder**:
1. BFS 走 **DB id-tree**:用 `DbGetOrderedSubFolderIDs(fPath, _showAllFolders)` 取 `(path, eid, sid)` 純資料 tuple,**不呼叫 GetFolderFromID**。
2. 每節點 mc 從 `DbGetFolderStats(path).mc` 拿(或沿用 FillCacheFromDbRow 填好的 `_cacheMailCount`)。
3. 聚合 mca/fca/fsa **在記憶體 bottom-up 重算**(沿用 Step3 `SummarizeSubTreeBottomUp`)→ 模式天然正確。
4. **僅在真正 cache miss(DB 沒這節點)才退到 ③ COM 物化**(冷快取/首次路徑保持原樣)。

**效益**:~120ms DB 走樹 + 殘餘記憶體運算,對比現況 5-7s,暖重啟 ~40-50×。
**代價**:零 schema 改動、零 snap、零模式標記(因聚合重算非信 DB)。
